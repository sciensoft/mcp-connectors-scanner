# Run the scanner as a system service like the application's

## Request
The scanner was not running, so the application's security pages returned 503. Make it follow the system unit
pattern of the application's `host/mcp-connectors.service`, enable it so it starts at boot, validate the unit, and
start the scanner through it.

## Reasoning
The cause was a host reboot on 18 November: nothing restarts the scanner container afterwards. The application stack
comes back because its own system unit runs `make up` at boot; the scanner had only the weekly sweep timer, which
starts a separate one-shot container.

The new unit copies the application unit's shape: a system unit under `/etc/systemd/system`, running as the user who
owns the checkout, wanted by `multi-user.target`, with the same restart policy and journal output. Four choices
differ on purpose. It runs `make serve` instead of `make up`, which keeps the container in the foreground so the unit
is `active` while the scanner runs, a crash is restarted and `systemctl stop` really stops it (the application unit
exits at once and shows `inactive` while its stack runs). It is ordered after `mcp-connectors.service` but does not
`Want` it, because that unit runs `make up`, which recreates the application's containers, so starting the scanner
by hand would have bounced production. It waits up to two minutes for the networks the application creates, since
ordering alone does not guarantee they exist at boot. And because this repository is public, the committed unit has
`@USER@` and `@REPO@` placeholders that `make host-install` fills in, as the existing user unit does with `@REPO@`.

Validated before and after installing: `systemd-analyze verify` passes on the filled-in unit, and a deliberately
broken copy is rejected with two errors, so the gate is real. The network wait returns at once when the networks exist
and keeps waiting when one is missing. After install the installed file equals the rendered repository file, the unit
is enabled, and starting it recreated the container with restart policy `no`, so systemd is its only supervisor. The
application's containers were not touched, the server stopped logging `scanner.grades_unavailable`, and the security
pages returned 200 again. Stop and start were also tested after a sweep had finished, so no sweep was cut short.

The test found a defect: the container ignores SIGTERM, so a stop takes the full 30 seconds and ends in SIGKILL
(exit 137). It is harmless today and is recorded as a todo rather than fixed here.

## Consulted rules
workflow.md - prompt file; workflow-security.md - a host service: it runs as the user and not as root, secrets stay in
the gitignored `.env` with mode 600 and never appear in the unit, and the public repository carries no user name or
path; workflow-todos.md - one new entry for the SIGTERM defect, and the sweep found nothing this change satisfies.

## Output
- `host/mcp-connectors-scanner.service`: the system unit, with placeholders.
- `Makefile`: `wait-for-networks`, `host-verify`, `host-install` and `host-uninstall`, plus help text. `host-install`
  verifies first, refuses to run as root, and refuses while the user service is enabled.
- `deploy/README.md`: a section on keeping the scanner running.
- `docs/todos/scanner-container-ignores-sigterm.md`.
