# Request

Run the scan automatically every night, and keep a public copy of the results in this repository, using a GitHub workflow. The scan itself should stay on the maintainer's own machine, because it has 32 threads and finishes in about four minutes.

## Reasoning

A GitHub-hosted runner cannot reach the catalog feed or the scanner database, and the scan runs untrusted third-party code, so the scan stays on the maintainer's machine, started by a systemd timer. The workflow only collects and publishes. It runs on a self-hosted runner on the same machine, which reaches the scanner's read-only API directly and needs no inbound port.

A scan trigger was considered as a new API endpoint and rejected: the API is read-only by contract, and the scanner already has a run-once mode. A separate one-shot container is safe because the always-on scanner wipes its work folder around every sweep, so two sweeps must not share one; each container has its own work area, and results are separate rows, with the latest one winning by time.

The runner is deliberately not given the container engine. A rootless engine socket would let a compromised job control every container on the machine, including the database.

Publishing: a release holds the full results (about 11 MB), and a compact summary is committed to a `scan-results` branch. A release alone does not reliably keep a schedule alive: sources disagree on whether it counts as activity, and a scheduled workflow in a public repository is switched off after 60 days without it, silently. A commit does count.

The data was not publish-safe as it stood: 15 results carried internal work paths and 5 mentioned an internal host name. `collect.py` scrubs those and a second check refuses to write the files if anything suspicious remains. Testing against the real data found two defects in my first version, both fixed and now pinned by tests: the host pattern also matched inside public package names such as `awslabs-aws-diagram-mcp-server`, corrupting 214 of them, and it missed hosts written as URLs.

## Consulted rules

workflow-security.md (public data leaving a production machine, secrets, a runner on a public repository), workflow-testing.md (scrubber tests in both directions).

## Output

- `deploy/sweep-once.sh`, `deploy/systemd/` (timer at 02:30, service), `deploy/collect.py`, `deploy/README.md`.
- `.github/workflows/nightly-scan.yml`: schedule 04:30 plus manual run only; job limited to this repository, `main`, and those two events; checks the newest scan is under 30 hours old before publishing.
- `tests/test_collect.py`: 15 things that must be removed, 9 public names that must stay, guard and nested-data cases. 66 tests pass.
- Repository settings: approval required for all outside contributors' workflow runs; actions must be pinned to a full commit hash; the checkout action is pinned to v7.0.1.
